## Problems (what is actually in the way)

1. **Serum crashes on LFO rate writes.** Which value crashes is unknown (the supervisor only knows the parameter). Until found, those six are unsafe to write and cannot be qualified; the compiler must not be able to emit them.
2. **306 controls need live-UI semantics, and the GUI is the slow observer.** The Serum browser's next-arrow drops clicks, ~4 presets per tool call, no image files are persisted. Doing 306 controls x ~5 edge presets one at a time (~1,500 presets) is not realistic.
3. **State readback is not the effective range.** 50 controls have a stored range different from the declared one (e.g. `env*.attack` reaches 30 vs 10 declared, `env*.hold` 15.6 vs 5.2, `fx.delay.feedback` 100 vs 90, `global.bend_range_up` -24..24 vs 0..48, `global.swing` 12.5..87.5 vs 0..100, `arp.velocity.target` 127 vs 100, `fx.flanger.rate` 20 vs 10). 7. **Environment fragility:** one Ableton crash mid-GUI-session (cause undetermined), stray-click side effects on the user's Live set, RAM pressure (~1.2-3 GB free), a network-dependent producer test that takes ~16 min and fails intermittently (pre-existing, unrelated).
8. **Scale still ahead:** 560 UNKNOWN + 135 structural + promotion + compiler + end-to-end are all unstarted at scale.

## Proposed next step (fast path, no shortcuts)

**A. Bisect the six LFO-rate crashes** (small, safety-critical): rerun `lfo1.rate` one value per subprocess (the planned vector is ~11 values) to find the crashing value(s); record them as a hard "never write" rule; repeat for lfo2..6 to confirm they share it.

**B. Replace preset-per-parameter GUI verification with multi-parameter GUI presets.** The Serum UI shows a whole module at once, and isolation is already guaranteed by the engine (a state diff proves only the intended keys differ). So build, per context/module, a small fixed set of GUI presets in which **every parameter of that module is set at the same time** to a distinct non-default value:
   - preset 1: every parameter at a distinct mid value (identity + value mapping via tooltips/readouts, all controls of the panel in one screenshot);
   - preset 2: every parameter one step beyond its state-clamped maximum (effective upper range / clamp);
   - preset 3: every parameter one step beyond its state-clamped minimum.
   That is about 3 presets per module (~60-80 in total) instead of ~1,500, and it produces the effective-range column that problem 3 requires. Where a control has no readout, a tooltip hover gives the internal name + value (proven on `A Uni Blend`, `A WT Pos`, `A Warp`, `A Coarse Pitch`). Discrepancies between GUI and state become explicit findings, never averaged.
   GUI reading stays a separate observer layer and is recorded in the same evidence format (`gui_*_evidence`, merged by `merge_range.py`).
